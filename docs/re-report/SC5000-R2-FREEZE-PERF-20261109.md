## 结论与验收状态

## 冻结抓取与实际证据

新增 `tools/ui-mod/capture_freeze.sh`，只从设备 `/tmp` 运行。它跟踪新的 journal，不用历史冻结日志触发；每四个采样周期检查冻结消息；主线程 utime 10 秒不变时标记为 suspect（不直接判定死锁）。触发会保存 Engine、两个 OfflineAnalyzer 的全部线程 stat/wchan/syscall/sched/status 指定字段、chrt、进程 maps、系统负载和 `/proc/locks`。ARM futex syscall 240/422 的等待地址附近也会读取 96 字节，并单独保存此次 syscall，便于后续分析。

该设备没有 `/proc/<tid>/schedstat`，`/proc/<tid>/sched` 也没有 wait_sum；没有可用的 sched_switch tracepoint 文件。故 R 态采样与 CPU tick 只能证明采样点的状态，不能给出精确 runqueue 等待时间。R 还可能表示正在运行；采样间也可能睡眠/运行，不得把以下跨度直接当作连续饥饿时长。

| 项目 | L | R |
|---|---:|---:|
| 抓取首/末 UTC | 01:25:11 / 01:46:13 | 01:25:13 / 01:46:18 |
| 主线程样本 | 2103 | 2108 |
| journal-freeze / cpu-stall 触发 | 0 / 0 | 0 / 0 |
| 后段实际采样间隔中位数 | 0.56 s | 0.56 s |
| 最大间隔（含采样脚本切换/服务重启） | 1.33 s | 4.78 s |

脚本在核对 BusyBox od 参数、ARM time64 syscall 号等过程中有短暂停顿并重新启动；21 分钟是首末覆盖范围，不是无缝且严格 0.5 秒的记录。`all.tsv` 是后段增加的全线程记录，早段只有主线程与降级线程。手工 healthy snapshot 已在两端验证，包含完整线程快照和可读的 futex 周边字节；它们不是冻结现场。

| 设备 / 线程 | PID / TID | 观测 R 跨度 | CPU tick 增量 |
|---|---|---:|---:|

| L OfflineAnalyzer / Network Exchang | 23636 / 23926 | 2.77 s | 0 |

OfflineAnalyzer 内的网络线程继承旧的 SCHED_IDLE/nice19，改用公平调度可以消除这一继承路径；不能据这些行认定锁依赖。SysfsWatcher 是原生 idle 线程，不在本次 hook 名单里，未在修复中强行改动它。

原验收的 `original-freeze-R.txt` 从首轮 `evidence.tar.gz` 中提取。它记录 Main_probe 1588 冻结和 futex_do_wait，但缺少冻结时全部线程 syscall/内存，无法补推出持有者。普通 Qt futex 的值可能是条件变量/等待序号，不一定是 owner TID；`/proc/locks` 也不是 futex 锁表。

本次重启再次记录 Engine 自己输出 `Flush to zero not applied` 和 `BFQ scheduler applied with strict_guarantees`；读取 mmcblk0 证实 `[bfq]`、strict_guarantees=1。它们仍是原生风险线索，没有本轮因果证据，未通过修改原生音频浮点模式或 BFQ 行为来“修复”。

## 调度 A/B 与 load

未部署新 hook。两组 A/B 都只在运行时把所有采样到的 SCHED_IDLE 或 nice19 线程切到 OTHER/nice10/BE7，保留原 CPU0/3 亲和度；这比最终 hook 名单宽，还包括部分原生低优先级线程。实验后按 manifest 恢复 policy、nice、mask、I/O，每端 17 个线程逐项比较，零不一致。

第一组是各 60 秒的 EMain/SceneGraph perf 对照。第二组 baseline 约 60 秒、公平调度约 180 秒，load 比较取每段最后 60 秒；标注了真实采样 uptime。第二组主/渲染线程 CPU 与分析器 CPU均由 task/stat 差分计算，CLK_TCK=100。

| load1 最后 60 秒范围 | 5.23–5.80 → 5.04–5.58 | 4.28–5.69 → 4.60–5.23 |

没有足够证据表明调度修改显著降低 load 或 GUI 工作量。两个分析器仍常驻，但在此空闲窗口并非主要 CPU 消耗者。也不能由 CPU 低推断它们永远不贡献 D 态或 load。

采样有可见开销：R 的 ps 快照中，抓取 shell 的累计 CPU 约 15.8%，A/B shell 约 8.3%（百分比按一个 CPU）。这些不是严格区间 CPU 差分，却足以说明观察者不可忽略；两段工具相同，绝对 load 不能直接与首轮无工具场景比较。第一组 perf 的时间戳是读取 ring 时的时间，约有轮询延迟；没有调用栈，也不是硬件 PMU 或帧时间测量。

## 拿不准

1. **冻结因果和 owner 未证实**：监控未复现，不能把 futex_do_wait、低优先级线程存在或 R 采样跨度单独当作锁反转结论。需下一次现场使用新抓取工具，再结合等待地址、Qt 锁实现和全部线程调用栈定位。
2. **逐曲接口未证实**：仅找到 AddTrackToAnalysisQueue、TracksInProgress 等 native 字符串，没有可靠 ITrackDataPtr 构造、生命周期和完成回执。按 PM“拿不准自行决定并报告”的指示，选暂禁自动全库提交，未伪装成已实现队列。恢复功能前必须证明逐曲适配器，并测 missing、临时目录含 symlink/realpath、双任务竞争、播放状态不明/过期等拒绝条件。
3. **播放测量未完成**：没有为获得控制/帧日志而违反最终“不部署”权限。PM 集成候选后，仍需短曲 ≤2 分钟、测完暂停，连续记录真实 PlayState、帧间隔及两线程 perf，才能给播放改善结论。
4. **根因覆盖范围有限**：原生 SysfsWatcher 的 idle、RT 音频固有亲和度、BFQ strict_guarantees、FTZ 警告均未擅改。不能从本轮空闲 CPU 占比推断其无关。
