## 第一阶段：补齐当前体验

1. **BPM 灯每拍变色一次**：定时间隔从 `60000/BPM/2` 改为 `60000/BPM`，
   每拍色相步长 1/4，四拍走完一圈。保持只写 `/Engine/Deck<N>/Color` 的内存属性。
   120 BPM 应为 500 ms，150 BPM 应为 400 ms；停止时沿用 100 ms 慢速流动。
   这是节拍周期跟随；真正跟随 Kick 的相位需要下一阶段读取已证实的拍点属性。
2. **小波形来源判定**：目前仅匹配音频路径中的 `Contents/`，无法区分该曲目是否已被 Engine 重算，
   也可能误认其他同名目录。下一步使用桥接曲目所有权与分析来源标记，经查询接口传给 QML；
   接口只读，按曲目切换查询，禁止每帧查询数据库。原生、串流、已重算曲目必须返回 1.0x。
3. **弹窗策略拆分**：Rekordbox 导入提示已屏蔽；另一个 drive profile 提示自动取 No。
   分别验证两种请求，保证没有偷偷启动原厂导入，也没有加载 U 盘 profile。
4. **Stems 如实显示**：当前按钮执行分轨或按 Stems 排序，并非只显示分轨歌曲的列表。
   先验收短曲渲染、取消、后端不可用、四分轨播放，再研究列表能力开关；
   不把所有机型能力检查一概改成 true。

## 第二阶段：Rekordbox 完整性与秒读

当前最优先的架构缺口在 `pkg/bridge/bridge.go:ConvertAtMount`：

- 超过 500 首的首次导入使用 `opts.Fast`，省略 Cue、Loop、波形和封面，载入后由 Engine 分析。
  因此「快速进歌单」不能表述为「全部打点/波形零扫描秒读」。
- stamp 只比较 `export.pdb` 的大小/mtime 和 `m.db` 非空，不覆盖 ANLZ、音频和完整导入状态。
  普通 `Convert` 的细粒度增量检查不能弥补在挂载入口提前返回的情况。
- 现有文档记录 6000 首变更检查约 24 秒，而 hook 预算只有 20 秒。
  不能简单延长阻塞，也不能恢复 Engine 已打开数据库时的后台写入。
- `fastImport` 分两次替换 state 和 m.db，需要验证断电/拔盘留下的版本组合及回滚。

实施顺序：

1. 建立版本化 manifest，至少记录源库身份、导入器版本、schema、导入模式、曲目总数及完成标记。
   使 metadata-only 与 full 明确可区分；未完成、模式升级或 state/db 不配套时不能旁路。
2. 为 ANLZ 与音频变更定义明确的检测策略。预先计算 manifest 可用于快捷验证；没有可靠快照时，
   完整校验仍需枚举文件，不能承诺任意 U 盘都 O(1)。
3. 构建候选数据库与 state 在独立目录，完成 SQLite integrity/foreign-key 检查后才进入发布。
   设计双文件发布与中断恢复协议；Engine 打开前完成，旧原生记录及播放端编辑不能丢失。
4. 优化 PDB/ANLZ 访问和全量导入，先在真实导出盘副本上量首导、无变化、单曲修改和歌单修改，
   再决定能否在挂载预算内发布。超预算保留上一个完整版本，提供显式离线准备流程。
5. 用一份真实 Rekordbox 导出和 Engine 对照库逐项比较 Hot/Memory Cue、Loop、拍线、颜色、
   歌单顺序和重算行为；源 `PIONEER/` 与音频做前后哈希对照。

「1–2 秒」仅作为特定盘/已准备缓存下的测量目标。旧记录中的约 30 ms 是 stamp 命中的旁路时间，
不包含首次解析/完整导入，也不等于界面已经可选曲播放。

## 第三阶段：定向逆向与局域网扩展

- REA 优先追踪：Stems 列表模型插入分支、`hasStemsPreRenderedPlayback()` 的调用者、
  overview/滚动波形消费端、PerformanceData 未知字段及拍点相位属性。
  每项记录 Engine 哈希、地址类型、调用关系、原始字节及反例；保留现有 expected-byte 全匹配保护。
- Memory Cues 的扩展表保存不等于原厂 UI 完整展示，另做只读 Memory-bank 视图方案，
  不占用或自动覆盖 Hot Cue A–H。
- Pro DJ Link 目前只有被动发现与状态读取。dbserver TCP 12523、NFS 取曲与电脑曲库浏览
  是单独的传输项目，按发现 → 元数据 → 取曲 → 加载验收，不写成已完成的 Rekordbox 直连。
